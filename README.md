# 穗云智策 · 空地协同精准植保智能决策云平台

面向小麦病害防控的空地协同精准施药系统的云端平台重构版本。

**公网访问地址**：https://mediator-cmd.github.io/suiyunzhice-platform/

**一句话**：植保无人机负责空中广域巡查，地面监测机器人负责近距复核，云端平台完成实时数据接入、三者联动决策、六维统计分析与自动路径规划，最终向农户交付"今天该做什么"的可执行结论。

---

## 一、平台回答的四个问题

| 老师的要求 | 平台对应能力 | 所在页面 |
|---|---|---|
| 无人机的数据怎么跟云端传输？实时性怎么保证？ | WebSocket 主通道（5–10Hz + 逐帧 ACK 计时）+ HTTP 批量补传（弱网兜底）+ MQTT 扩展预留；端到端时延、P95、丢包率、RTT 全程可查 | 实时监控 |
| 数据统计分析分哪些维度？对农户有什么用？ | 空间 / 时间 / 病害 / 平台 / 作业 / 环境 六维；**每一维同时输出可执行的农户结论**，不只是图表 | 数据分析、农户服务 |
| 小车和无人机的数据怎么互相整理统计？三者怎么实时联动？ | 空中发现 → 云端判据 → 派单机器人 → 近距复核 → 云端确认 → 靶向喷洒 的闭环；每段时延逐段可查 | 空地联动 |
| 大面积喷洒怎么飞？速度与喷洒比例怎么调？轨迹怎么最经济/最快/最环保？ | 航向 × 速度 × 喷幅三维联合搜索，三目标加权打分；速度-喷洒比例自动求解并给出可行区间；与人工手画航线量化对比 | 路径规划 |

## 二、技术栈

- **前端**：React 18 + Vite 6 + Recharts + Leaflet（`web/`）
- **服务端**：Node 22 + Express + ws + `node:sqlite`（零原生依赖）（`server/`）
- **共享内核**：`shared/` —— 数据契约与全部业务算法，**前后端跑同一份代码**

```
挑战杯/_大创平台/
├── shared/                  ← 前后端共用的内核
│   ├── schema.js            统一数据契约（遥测帧/识别结果/任务/联动事件）
│   ├── planner.js           路径规划求解器（航向/速度/喷幅搜索 + 速度-喷洒比例）
│   ├── analytics.js         六维统计 + 农户简报
│   ├── linkage.js           空地联动决策引擎
│   ├── simulator.js         数据模拟器（无设备时演示）
│   ├── linkstats.js         链路质量统计（时延/P95/丢包率）
│   ├── spraydispatch.js     靶向施药派工（确诊病灶 → 分区作业单 + 节药率）
│   ├── platform.js          平台内核：地块定义、规划缓存、元数据
│   ├── tenancy.js           多租户与角色权限（5 类主体 / 5 种角色 / 14 项权限）
│   ├── deviceaccess.js      设备接入鉴权（API Key / 心跳在线 / 指令闭环 / 接入健康度）
│   ├── metering.js          计量与结算（按亩施药 / 按亩巡查 / 按架次 / 按次）
│   ├── openplatform.js      开发者门户（接入五步 / 代码样例 / 接入模拟器）
│   ├── mobile.js            掌上端内核（田间作业模式 / 断网补传 / 三端职责）
│   ├── farmer.js            农户服务层（公众号推送：平台给事实，大模型给表达）
│   ├── demo.js              演示数据种子（租户 / 成员 / 设备 / 用量）
│   └── memstore.js          内存存储（纯静态部署用，接口与 SQLite 版一致）
├── server/src/
│   ├── index.js             HTTP + WS 入口、REST API
│   ├── hub.js               实时数据接入（WebSocket 通道）
│   └── store.js             SQLite 持久化
├── web/src/
│   ├── api.js               API 客户端 + 实时订阅 + 浏览器端降级引擎
│   ├── components/FieldMap.jsx
│   └── pages/               14 个功能页面
├── deploy/                  Dockerfile / compose / nginx / deploy.sh / 自检脚本
└── .github/workflows/pages.yml   GitHub Pages 自动发布
```

**为什么要这样分层**：平台的所有结论（药液用量、节约率、闭环时延、规划得分）
都来自 `shared/` 里的算法。真实部署时它们跑在 Node 服务端并落到 SQLite；
纯静态部署时同样的代码跑在浏览器里、用内存存储。
**两种环境下页面显示的数字口径完全一致**，申报材料里引用的数值不会因为演示环境改变而对不上。

## 三、平台底座：把「一个演示」变成「一个平台」

这一节是平台从演示走向可运营系统的关键。判断一个云平台是不是"真平台"，
不看首页有多少图，而看它能不能同时回答：**谁在用、用的谁的设备、干了多少活、
该向谁收多少钱、第三方设备怎么接进来**。

### 3.1 多租户与权限（租户与权限页）

平台面向三类付款方：**平台运营方、合作社 / 农场、作业服务队**，外加监管单位。
每类主体能看到的字段、能做的操作都不���同，因此权限矩阵是平台的硬约束，
不是界面上的装饰。

| 角色 | 数据范围 | 典型权限 |
|---|---|---|
| 平台运营方 | 全平台 | 租户管理、成员管理、设备签发与吊销、全量账单、经营看板 |
| 农场主 | 本农场 | 查看本农场地块与账单、指派作业、吊销本方设备密钥 |
| 作业手 / 飞手 | 指派给本人 | 领单、执行点位、上传取证照片、异常上报 |
| 农艺师 | 指派地块 | 病种复核、策略配置、施药建议审核 |
| 监管方 | 全平台只读 | 监管统计、作业记录追溯 |

- 权限矩阵共 14 项权限，逐项在页面上以 ✓ / — 呈现。
- 越权调用返回 403 并说明缺少哪项权限；传入未登记身份返回 401，**绝不降级为管理员**。
- 所有写操作都做归属校验：A 租户不能管理 B 租户的设备或成员。

### 3.2 设备接入（设备接入页）

第三方植保机、机器人都不是本项目造的，平台必须能纳管别人的设备。

```
签发 API Key  →  设备注册  →  心跳保活  →  遥测上报  →  指令下发与回执  →  计量结算
```

- **API Key**：`sk_<deviceId>_<盐值>`，盐值由服务端派生并**只存盐不存明文**，
  明文仅在签发时展示一次；支持吊销与恢复。
- **在线判定**：心跳超时 15 秒判离线，由心跳驱动而非由前端心跳驱动。
- **指令闭环**：下发 → 已确认 → 执行中 → 完成 / 失败 / 超时，
  每段单独计时（派发时延、端到端时延），可逐条查。
- **接入健康度**：由丢包率、P95 时延、指令闭环率合成打分，分四档。
  这是平台对接入方最实在的一个数字 —— 它决定了平台敢不敢接第三方的活。

### 3.3 计量与结算（计量结算页）

平台要能开商业账单，就必须先定义清楚**按什么计量**。四条计量口径：

| 计量单位 | 单价 | 说明 |
|---|---|---|
| 按亩施药 | ¥12 / 亩 | 只对实际喷洒面积计费 |
| 按亩巡查 | ¥3 / 亩 | 只对实际巡查面积计费 |
| 按架次 | ¥20 / 架次 | 换药 / 补给的架次成本 |
| 按识别次数 | ¥0.8 / 次 | 病害识别调用 |

**施药面积与巡查面积分开计量**，避免同一块地同时被巡一遍、喷一遍
时按两种单价重复计费。账单按 `missionId` 去重、按自然月分账期。

### 3.4 开发者门户（开发者门户页）

平台不是封闭系统。第三方厂商的植保机要接进来，得有一份能照着做的接入文档。
门户给出**接入五步**（注册 → 心跳 → 遥测 → 指令 → 结算）、每一步的
端点 / 请求头 / 请求体 / 响应体样例、Node / Python / WebSocket 三种代码样例，
以及一个**接入模拟器**：点一下走完五步，拿到真实签发的 API Key 和模拟账单。

### 3.5 三端联动（三端联动页）

老师问的「三端的数据联动如何实现」，答案写在这一页里：

| 端 | 使用者 | 承载数据 | 联动方式 |
|---|---|---|---|
| PC 调度端 | 平台运营 / 调度员 | 地块态势、识别结果、作业单、指令 | 下发作业单与设备指令，接收回执 |
| 掌上端 | 作业手 / 飞手 | 点位清单、取证照片、识别结果、异常记录 | 领单 → 执行点位 → 拍照回传 → 异常上报 |
| 公众号 / 小程序 | 农户 | 病灶定位、病种、药剂、剂量、安全间隔期 | 订阅消息推送 + 深链回平台 |

三端跑的是**同一套判据、同一份作业单**，口径不会分叉 —— 这是平台的价值所在。

掌上端按田间场景单独设计，不是把 PC 页面缩小：最小触点 48px、
最小字号 15px、深底浅字、关键操作在屏幕下半区；**断网时取证帧进本地队列，
恢复网络后补传**，日志逐条可见。

公众号这一端做了明确的分层：**平台负责事实，大模型负责表达**。
病灶网格、病种、置信度、药剂、剂量、安全间隔期全部来自平台已确认的数据与策略库，
大模型只把这组事实改写成农户看得懂的话，**不允许引入新数字**；
大模型不可用时退化为模板表达，事实完全一致。

### 3.6 页面清单（14 页）

| 分组 | 页面 | 回答什么问题 |
|---|---|---|
| 态势 | 总览 / 实时监控 / 空地联动 / 数据分析 / 农情策略 / 路径规划 | 平台上发生了什么 |
| 平台底座 | 租户与权限 / 设备接入 / 开发者门户 / 计量结算 | 平台怎么运营、怎么接第三方、怎么赚钱 |
| 三端 | 三端联动 / 农户服务 | 三端怎么协同，农户拿到什么 |
| 方案 | 平台方案 / 系统架构 | 平台由什么构成，流程怎么走 |

## 八、规划模型说明

### 作业模式

| 模式 | 喷幅 | 适用 | 2 ha 示范田实测 |
|---|---|---|---|
| `full` 全田覆盖 | 4–7 m 整机喷幅 | 病害初发、尚未成片 | 15 条航线 / 3110 m / 6.56 min / 1 架次 / 25.2 L / 耗电 29.2% |
| `target` 靶向点喷 | 1 m 窄幅 | 病害已明确、只打有病的地方 | 19 个病灶格 / 95 条喷带 / 3.61 min / **0.57 L** / 靶向覆盖率 1.0、溢出 0 |

靶向模式药量仅为全田模式的 **2.3%**（节约 97.7%），这就是"精准施药"最直观的量化结果。

> 靶向模式的格数、簇数、时长随病灶的空间分布而变（簇按八邻域连通划分，
> 病灶越集中簇越少、转场越短、耗时越短）。上表是申报材料采用的那组
> 19 格单簇分布下的求解结果，可用 `shared/planner.js` 的 `autoPlan` 以该组
> 病灶网格复现；线上「路径规划 → 靶向点喷作业」页显示的是**实时识别结果**
> 所对应的靶向格数与指标，不保证与上表完全相同。

### 速度-喷洒比例

喷头流量必须与「前进速度 × 喷幅」严格成正比：

```
每米药液量 = 喷幅 × 目标施药量(L/ha) / 10000     ← 与速度无关
喷洒流量(L/min) = 每米药液量 × 飞行速度(m/s) × 60
```

由于每米药液量与速度无关，**流量 ÷ 速度 = 常数**（`flowPerSpeed`），变速时按此比例同步调整喷阀 PWM 占空比即可。平台同时给出可行速度区间：低于下限会断续喷雾，高于上限会漏喷。

### 三目标打分

- **经济**：总作业时长（含换药架次）+ 药耗 + 总能耗
- **快速**：航线总长 + 转弯航程 × 3
- **环保**：重喷率 + 转弯占比 + 靶向模式的非目标区溢出面积

权重可调（默认 0.4 / 0.35 / 0.25），在候选集内归一化后加权。搜索空间为航向 8 × 速度 5 × 喷幅 4 = 160 组可行解。

### 能耗与架次

- 巡航 0.0092 %/m，转弯段（减速+悬停）0.085 %/s
- 5 L 药箱：药液耗尽即需返航换药，架次 = ⌈药量 / 5 L⌉，每次换药约 6 min
- 参数标定参考申报书竞品表：极目 EA-30X 续航 22.7 min / 大疆 T25 续航 40 min

## 九、已知边界

- 能耗模型为简化标定模型，未经实测台架验证；申报书中的续航数据来自竞品对比表。
- 靶向网格由识别结果的置信度阈值（0.75）筛出，误检会带入非目标网格。
- `savedRatio`（药液节约率）只在存在喷洒任务时计算，否则显示"待作业"而非编造数字。
  口径为「整田均匀喷施（全田面积 × 12 L/ha）」对比「靶向点喷实际药耗」，
  页面同时标出对照基准，避免只看百分比。
- 联动时延中「执行到位」段为物理行程估计值，非实测。
- 演示模式下的数据来自内置模拟器，形状与真实设备一致但非真实采集；
  纯静态部署时数据只存在于浏览器内存中，刷新页面即重置。
- **气象读数是模型派生值，不是气象站实况**。平台按日序与时刻确定性生成，
  保证同一天内读数平滑、跨天有周期，任何时候刷新数字都自洽；
  所有对外呈现的地方都标注「模拟 / 模型派生」，不得以「实况」二字对外表述。
- **公众号推送的事实全部来自平台已确认数据**，大模型只改写表达、不生成事实；
  未配置大模型时退化为模板表达，事实一致。演示环境默认走模板。
- **计量与结算为设计口径**（单价来自商业模式设定），尚未接入真实支付通道；
  账单与经营指标用于说明平台的商业闭环，不是已发生的收入。
