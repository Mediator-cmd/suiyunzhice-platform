## 二、平台架构：为什么把它做成「可重构」的

### 2.1 原有问题

原平台由四个互不连通的软件著作权组成——视觉识别管理平台、感知行为与决策系统、病虫害爆发预警平台、小麦状态评估软件。设备数据、云端决策与前端展示各自为政，无法形成可复用的空地协同能力。

### 2.2 重构后的分层

```
┌──────────────────────────────────────────────────────────┐
│  展示层  React 18 + Vite + Recharts + Leaflet            │
│  8 个功能页：总览 实时监控 空地联动 数据分析                │
│              路径规划 平台方案 农户服务 系统架构          │
├──────────────────────────────────────────────────────────┤
│  平台内核  shared/  ← 前后端共用同一份代码                 │
│  ├ planner.js    路径规划求解器                            │
│  ├ analytics.js  六维统计 + 农户简报                       │
│  ├ linkage.js    空地联动决策引擎                          │
│  ├ simulator.js  数据模拟器                               │
│  ├ linkstats.js  链路质量统计                             │
│  ├ platform.js   地块定义 / 规划缓存 / 元数据              │
│  ├ memstore.js   内存存储（纯静态部署用，接口同 SQLite）    │
│  └ schema.js     统一数据契约（三端共用）                  │
├──────────────────────────────────────────────────────────┤
│  服务端  Node 22 + Express + ws + node:sqlite（零原生依赖）│
│  17 个 REST 接口 + /ws/telemetry（设备）+ /ws/live（前端） │
└──────────────────────────────────────────────────────────┘
```

### 2.3 关键设计决策：内核下沉，前后端跑同一套算法

把纯计算模块从服务端抽到 `shared/`，由服务端与浏览器**共享**：

- **真实部署**：内核跑在 Node 服务端，数据落 SQLite，前端经 WebSocket 实时接入（右上角显示「实时接入」）
- **纯静态部署**：内核跑在浏览器里，数据存内存（右上角显示「演示模式」）

**两种环境下页面显示的每一个数字口径完全一致。** 申报材料里引用的药液用量、节约率、闭环时延、规划得分，不会因为演示环境不同而对不上——这在评审现场是可以当场验证的。

> 顺带解决了一个实际问题：如果前端只做成静态壳子，路径规划这类核心能力在纯静态托管下就会失效，页面成了空壳。现在纯静态部署同样是完整可用的平台。

## 三、四个要求的技术实现

### 3.1 数据传输与实时性

**三层通道设计**

| 通道 | 路径 | 定位 | 说明 |
|---|---|---|---|
| WebSocket 遥测 | `ws://host/ws/telemetry` | 生产主用 | 长连接、低开销、可双向；遥测与识别结果同帧上送；云端逐帧 ACK 回传服务器时间戳，设备据此算 RTT 与端到端时延 |
| HTTP 批量补传 | `POST /api/ingest/batch` | 弱网必备 | 信号盲区缓存帧，恢复后批量上报，携带自增 `seq`，云端按 seq 补齐空洞并统计丢包率 |
| MQTT over WebSocket | `mqtt://host:8083/mqtt` | 后续扩展 | 设备数从 2 台扩到数十台时，发布/订阅模型比点对点省带宽 |

**实时性如何被证明**（不是口号，是可量化的数字）：

- 端到端时延 = 云端收到帧的时刻 − 设备采集该帧的时刻（设备端 `ts` 字段，Unix 毫秒）
- 丢包率 = 由 `seq` 空洞推算
- P95 时延、RTT 一并展示

实测（演示数据）：无人机与机器人平均端到端时延 **49–53 ms**，P95 **75–78 ms**，丢包率 **0.00%**。

### 3.2 六维统计分析与农户价值

| 维度 | 统计内容 | 农户拿到的结论 |
|---|---|---|
| 空间 | 按 5 m×5 m 网格统计密度与主病种 | 「网格 R12C25 检出 3 处，属高密度病灶，建议列入首批靶向作业」 |
| 时间 | 按日统计检出与施药节奏 | 「检出量较前一日上升 32%，病害进入扩散期，建议 48 小时内完成一次全田巡查」 |
| 病害 | 按病种分层，含发病部位 | 每个病种对应可执行防治建议（锈病初发期用药 + 7–10 天复查；根腐病必须近地确认……） |
| 平台 | 量化空地分工 | 「无人机完成 N 次空中识别（广度），机器人完成 N 次近距复核（深度）」 |
| 作业 | 按任务统计航时、药耗、覆盖 | 每次任务的时长、药耗、航速全量可查 |
| 环境 | 按时段分组的光照与置信度 | 「光照弱、湿度高，病害活性高且不易飘移，是喷施与复核的黄金窗口」 |

### 3.3 三者实时联动

```
① 空中发现    UAV 巡航采集，实时识别出疑似病斑
② 云端派单    按置信度 / 病位判定是否需近地复核
③ 机器人复核  地面机器人驶向目标，近距补拍叶下 / 根茎 / 土壤
④ 云端确认    融合空中与地面证据，确诊或排除
⑤ 靶向喷洒    下发无人机，任务中带上速度-喷洒比例参数
```

**判据是可解释的**（写在平台上，评委能看懂）：置信度 < 75%、或病位在叶下/根茎/土壤（空中天然看不见）、或病种为根腐病/赤霉病（需近地确认部位）→ 派单复核；否则直接喷洒。

**时延逐段归因**，这样才能知道慢在哪一段：

| 段 | 含义 |
|---|---|
| `sense` | 感知 → 决策 |
| `dispatch` | 决策 → 下发 |
| `act` | 下发 → 执行到位 |
| `total` | 端到端 |

### 3.4 路径规划（老师的核心提升点）

#### 3.4.1 两种作业模式

平台把「1 m 窄幅喷施机构」与「大面积喷洒」统一到一套模型里，用作业模式区分：

| 模式 | 喷幅 | 适用场景 | 2 ha 示范田实测 |
|---|---|---|---|
| `full` 全田覆盖 | 4–7 m 整机喷幅 | 病害初发、尚未成片 | 15 条航线 / 3110 m / 6.56 min / 1 架次 / **25.2 L** / 耗电 29.2% |
| `target` 靶向点喷 | 1 m 窄幅机构 | 病害已明确，只打有病的地方 | 19 个病灶格 / 95 条喷带 / 3.72 min / **0.57 L** / 靶向覆盖率 **1.0**、溢出 **0** |

**靶向模式药量仅为全田模式的 2.3%**，靶向覆盖率 1.0 且对非目标区零溢出——这就是「精准施药」最直观的量化结果。

> 靶向模式的簇数与耗时随病灶空间分布而变（簇按八邻域连通划分）。
> 上表是申报材料采用的那组 19 格分布下的结果，可在「路径规划 → 靶向点喷
> 作业」实时复现；页面上同时显示靶向格数、簇数、覆盖率与溢出面积。

#### 3.4.2 速度与喷洒速度的比例怎么调

喷头流量必须与「前进速度 × 喷幅」严格成正比：

```
每米药液量 = 喷幅 × 目标施药量(L/ha) / 10000      ← 与速度无关
喷洒流量(L/min) = 每米药液量 × 飞行速度(m/s) × 60
```

由于每米药液量与速度无关，**流量 ÷ 速度 = 常数**（`flowPerSpeed`）。变速时按此比例同步调整喷阀 PWM 占空比即可，平台自动求解并锁定该比值。

平台同时给出**可行速度区间**：低于下限会断续喷雾（超喷、药害），高于上限会漏喷（沉积不足）。示例（喷幅 1 m、12 L/ha）：流量 0.432 L/min，喷头开度 29%，**可行速度 3.13 ~ 20.83 m/s**，流量/速度比 0.072 L/(m·min) 恒定。

#### 3.4.3 轨迹怎么最经济、最快速、最环保

三目标加权打分，权重可实时拖动调整：

- **最经济**（默认 0.40）：总作业时长（含换药架次）+ 药耗 + 总能耗
- **最快速**（默认 0.35）：航线总长 + 转弯航程 × 3
- **最环保**（默认 0.25）：重喷率 + 转弯占比 + **靶向模式的非目标区溢出面积**

搜索空间：航向 8 × 速度 5 × 喷幅 4 = **160 组可行解**，在候选集内归一化后加权排序，排名第一的解可直接下发。

#### 3.4.4 与人工手画航线的量化对比

这是老师「效率太低」痛点的直接回应：

| 指标 | 人工手画 | 平台自动规划 | 改善 |
|---|---|---|---|
| 作业时长 | 18.49 min | 6.56 min | **−64.5%** |
| 航线长度 | 4784.1 m | 3110 m | **−35.0%** |
| 转弯占比 | 16.4% | 3.5% | **−78.4%** |
| 药液用量 | 26.88 L | 25.2 L | −6.3% |
| 重喷率 | 12.0% | 0.0% | — |

靶向模式下（对同一批病灶）：时长 **−52.6%**，航程 **−29.4%**，重喷率 12.0% → 0%。

需注意两个「节省」口径不同，不要混用：
- **相对人工手画**：靶向模式时长 −52.6%、航程 −29.4%（人工与自动用的是同一套 1 m 窄幅）
- **相对全田覆盖**：靶向模式药量 0.57 L vs 全田 25.2 L，**仅为 2.3%**（省 97.7%）—— 这才是「精准施药」的核心价值

## 九、已知边界（如实说明）

- 能耗模型为简化标定模型，未经实测台架验证；申报书中的续航数据来自竞品对比表（极目 EA-30X 22.7 min / 大疆 T25 40 min）
- 靶向网格由识别结果的置信度阈值（0.75）筛出，误检会带入非目标网格
- 药液节约率只在存在喷洒任务时计算，否则显示「待作业」而非编造数字
- 联动时延中「执行到位」段为物理行程估计值，非实测
- 演示模式下数据来自内置模拟器，形状与真实设备一致但非真实采集；纯静态部署时数据只存在于浏览器内存，刷新页面即重置
- 所有设备端数字均为演示数据；接入真实设备后由 `/api/ingest/batch` 或 `/ws/telemetry` 写入
